# Migração para PostgreSQL 18 — ERP Condomínios

As decisões abaixo já foram aprovadas pelo André. Não as reabra nem peça revisão de novo. O estado atual (o que já rodou, o que está bloqueado) está no fim de `AI-CONTEXT/DATABASE.md` §22.x: leia só a última subseção antes de agir. Servidor e bancos: skill `erp-condominios-infra-hetzner`.

## 1. Princípios
- Não há sincronização contínua. Cada rodada de teste faz: backup diário verificado → restore em `erp_pg_source` → recarga integral de `erp_pg_dev`.
- O pipeline nunca conecta ao MySQL de produção. A virada P5 segue: congelar entradas → dump final → restaurar em `erp_pg_source` → carregar o PostgreSQL definitivo.
- MySQL continua padrão até a virada. `ERP_DB_DRIVER` aceita `mysql` (default) ou `pgsql`.
- Diferenças aceitas são só as da tabela abaixo. Qualquer outra diferença na reconciliação bloqueia.

## 2. Regras de tipo aprovadas
| MySQL | PostgreSQL |
|---|---|
| DATETIME | `timestamp(0)`, sem conversão |
| TIMESTAMP | Lido em UTC, gravado como `timestamp(0)` na hora civil de America/Sao_Paulo |
| TIME | `time(0)` se todos os valores estão entre 00:00:00 e 23:59:59; `interval` só quando há valor negativo ou acima disso (coluna listada) |
| tinyint | `smallint`, nunca boolean |
| int unsigned | `bigint` |
| bigint unsigned | `bigint` + `CHECK (>= 0)`; `numeric(20,0)` só se a pré-varredura achar valor acima de 9.223.372.036.854.775.807. Os dois lados de uma FK sempre com o mesmo tipo |
| decimal(p,s) | `numeric(p,s)` |
| json | `json` |
| blob | `bytea`, byte a byte |
| ENUM | `varchar` + CHECK com os rótulos, incluindo valores legados fora da lista |
| AUTO_INCREMENT | `GENERATED BY DEFAULT AS IDENTITY` + `setval` após a carga |
| DEFAULT CURRENT_TIMESTAMP | `LOCALTIMESTAMP(0)` |
| ON UPDATE CURRENT_TIMESTAMP | Trigger genérica: atualiza só se a linha mudou e a coluna não foi definida no UPDATE |
| DEFAULT literal de texto (inclusive `''`) | Copiado igual, sem revisão. Só default que é expressão ou função não mapeada bloqueia |
| Data zero | NULL. Se a coluna era NOT NULL, vira nullable e é listada |
| NUL em texto | Removido; original em `legado.auditoria_nul`. NUL em binário fica intacto |
| Texto | Collation `ci`. Colunas `_bin` ou com nome de token/hash/senha/chave/slug/uuid/caminho usam `COLLATE "C"`. UNIQUE que colide sob `ci` → coluna em "C" |
| Índice de prefixo ou TEXT | `left(col, n)`. FULLTEXT é adiado |
| Coluna gerada | Traduzida como STORED e excluída do COPY. Hoje só `lancamentos_agua.consumo` |
| Tabelas de backup (`_backup`, `_bkp_`, `_old`, `_AAAAMMDD`) | Schema `legado` |
| FK | Criada NOT VALID, depois VALIDATE. Órfãos são contados, nunca apagados |
| Procedures | Não migradas: o PHP tem zero `CALL` |
| 7 triggers de negócio | Versão tenant-scoped em `sql/postgresql/070_business_triggers_tenant_scoped.sql`, aplicada após a carga |

## 3. Ferramentas
- `tools/migracao_pg/rebuild.sh`: pipeline oficial com perfis `development` e `cutover`. Faz catálogo, DDL, loader e reconciliação com hash por linha.
- `tools/migracao_pg/carga_rapida_pg.py` (branch `pg/carga-rapida`): carga direta já provada com dados reais (276 tabelas, 11/11 FKs). É o caminho alternativo da virada. Recusa origens de produção e destinos fora da allowlist.
- Depois de toda recarga: reinstalar as 7 triggers, neutralizar integrações (SMTP, FCM, WhatsApp, ControlID, câmeras, pagamentos) e conferir contagens ativas zeradas.
- Relatórios trazem só agregados: tabela, coluna, contagem, SQLSTATE, duração.

## 4. Runtime PHP no PostgreSQL
- Shim drop-in em `api/db/`: `PgsqlMysqliConnection`, `Statement` e `Result` com aliases `mysqli*` e 26 funções em `MysqliDropInFunctions.php`. Só é ativado no pool sem mysqli nativo.
- `insert_id` vem de `RETURNING` da própria linha. Nunca de `lastval()`.
- `MysqlToPostgresSqlTranslator.php` traduz o SQL legado. Em modo estrito, o que ele não traduz gera `SQL_NAO_TRADUZIDO` no log: corrija na origem, não silencie.
- DDL em tempo de execução (CREATE/ALTER dentro de API) fica protegido por `if (DatabaseDialect::isPostgres()) return;`.

## 5. Código novo ou alterado: SQL portável
- Use SQL comum aos dois bancos. Evite crase, `INSERT IGNORE`, `ON DUPLICATE KEY UPDATE`, `DATE_FORMAT`, `IFNULL`, `GROUP_CONCAT`, `LIMIT x,y` e `SHOW ...`.
- Diferenças inevitáveis ficam em `DatabaseDialect`/helpers, escolhidas por `ERP_DB_DRIVER`.
- Toda migration nova precisa de versão MySQL e PostgreSQL, ou de registro explícito da pendência.
- Rode `php tools/pg_sql_lint.php <arquivos alterados>`: o PR não pode aumentar findings.
- Arquivos mortos (teste_, debug_, diagnostico_, backups, `testeAPI/`, `error/`) ficam fora do lint e do deploy; não os corrija.

## 6. Virada P5 (resumo)
Os gates são: teste manual do André no 8443 sem erro bloqueante, carga com reconciliação 100%, zero `SQL_NAO_TRADUZIDO` em fluxo usado e triggers testadas.

Sequência:
1. Nginx em 503, exceto o IP do André. Crons desligados.
2. Dump final em `/var/backups/erpcondominios/mysql-final/`, validado.
3. Restore em `erp_pg_source`.
4. Carga no banco definitivo, com triggers e reconciliação.
5. Troca de driver e config.
6. Smoke e liberação.

Rollback: voltar ao MySQL, mantido intacto por 7 dias. Backup PostgreSQL com `pg_dump -Fc` diário, retenção de 14 diários e 8 semanais.

Nada disso é executado sem ordem explícita do André.
