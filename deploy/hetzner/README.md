# Runbook Hetzner — ERP Condomínios HML

## Limites de operação

Este host serve HML pelo IP `2.29.161.106`. Não altera DNS, HostGator ou produção. MySQL 8.4 permanece somente em socket/localhost; nunca liberar 3306. Não modificar SSH, fail2ban, UFW ou AppArmor neste runbook. Integrações externas na HML permanecem neutralizadas. O ZIP de `uploads/` e `config/firebase/` ainda precisa ser entregue; não preencher esses diretórios com dados de produção até autorização.

## Release da aplicação

A fonte é exclusivamente `ASOARESBH/app.erpcondominios.com.br-`, branch `main`. Criar um diretório novo `/var/www/erpcondominios/releases/<SHA>`, transferir apenas os arquivos rastreados no SHA aprovado, não extrair sobre uma release existente e manter o código `root:www-data`, sem permissão de escrita para PHP. `current` é um symlink atômico para uma release. Mantenha cada release anterior para rollback e nunca inclua `.git`, segredos ou dados de upload no document root.

A configuração privada DB reside fora do webroot em `/etc/erpcondominios/erp_config.php`, `root:www-data 0640`; o segredo é mantido root-only em `/etc/erpcondominios/secrets/`. Não imprimir, versionar, transferir por chat ou copiar para logs. O host recebe o código de `main`; os scripts deste diretório documentam infraestrutura e não substituem o código de aplicação.

## Nginx e TLS de IP

A configuração de site é `nginx-ip.conf`, instalada como `/etc/nginx/sites-available/10-erpcondominios-ip.conf`; cópias de rollback locais preservam configurações anteriores. Validar sempre `nginx -t` antes de `systemctl reload nginx`. HTTP redireciona ao HTTPS somente para o IP; o default HTTP existente permanece inalterado. No TLS, o vhost principal serve HML pelo IP e o catchall apresenta o certificado IP e encerra com 444 para `Host` desconhecido. O certificado IP fica sob `/etc/letsencrypt/live/erpcondominios-ip/`, tem validade curta e não é wildcard de domínio. Não emitir certificado para hostname sem autorização DNS.

O vhost serve somente extensões de conteúdo permitidas, PHP existente fora de pastas internas bloqueadas, e HTML estático; extensões não permitidas retornam 404. Dotfiles, `.htaccess`, arquivos de configuração, logs, fontes, `vendor`, testes e diretórios operacionais são bloqueados. PHP enviado não é executado; `/uploads/` encaminha para a API autenticada. Mudanças no artefato precisam ser conferidas contra `origin/main` e testadas com `nginx -t` e smoke de rotas.

Certbot Snap renova por seu timer. O deploy hook executa `nginx -t` e recarrega o serviço após renovação válida. O `renew --dry-run` em staging passou em 12/11/2026. Verifique `systemctl list-timers`, `snap services certbot`, `certbot certificates` e o healthcheck. Certificado IP `shortlived` dura 160 horas; a renovação automática funcionando é requisito operacional. O drop-in `snap.certbot.renew.service.d/10-erpcondominios-alerts.conf` aciona o dispatcher via `OnFailure`; não copie o journal para e-mails.

## Backup e verificação

Antes de habilitar o timer, provisionar `/var/backups/erpcondominios/daily/` como `root:root 0700`; a unit permite escrita apenas neste diretório e `/run/lock`. O script `backup-db.sh`, instalado como `/usr/local/sbin/erpcondominios-backup.sh`, exporta somente o schema selecionado pela configuração privada ativa via socket local, com routines, triggers, events e blobs. O timer diário (06:15 UTC, com atraso aleatório curto) chama o service root-only. O script usa lock, exige pelo menos 10 GiB livres, comprime, testa `gzip -t`, calcula SHA-256 e cria dump/manifesto como `root:root 0600`. A saída do job vai ao journal e não contém linhas do dump. A automação não expurga backups.

O script resolve `ERP_DB_NAME` do arquivo privado `/etc/erpcondominios/erp_config.php` em runtime, valida o nome contra uma allowlist de schemas ERP e confirma que o schema existe antes do dump. Assim, quando a configuração ativa for alternada para uma cópia restaurada, os backups acompanham a base efetivamente servida, sem editar o script ou imprimir credenciais. A cópia HML anterior deve continuar preservada; não renomear nem remover schemas como parte da troca.

`erpcondominios-backup-integrity.service`/`.timer` executa diariamente às 07:00 UTC, após o backup. Valida o `gzip -t`, checksum SHA-256 e os modos `0600`; grava somente um marcador root-only em `/var/lib/erpcondominios/backup-integrity-verified-at`. O healthcheck passivo executado a cada cinco minutos não inicia/reinicia serviços; confere Nginx/PHP-FPM/MySQL, conexão MySQL por socket, HTTPS local, validade TLS menor que 72 horas, ao menos 15 GiB livres, idade do último backup (até 36 horas) e idade do marcador de integridade. A saída do journal contém somente resultado agregado e IDs de item, sem corpo do e-mail ou erro bruto do msmtp.

Para verificar sem expor conteúdo: `systemctl status erpcondominios-backup.service --no-pager`, `journalctl -u erpcondominios-backup.service`, `gzip -t <arquivo>` e `sha256sum -c <manifesto>` executados dentro do diretório privado. Não usar `cat`, não enviar dump/hash por chat/Git e não redirecionar stdout para arquivos não privados. Antes de qualquer DDL, executar e validar backup novo.

Os dumps são mantidos apenas no mesmo host e não têm retenção/expurgo automático; é um risco residual de perda do volume. O crescimento do espaço deve ser acompanhado até aprovar uma política de retenção que preserve a cópia histórica exigida. Uma cópia off-host criptografada e um exercício de restore são pendentes. Nenhum teste de restauração deve sobrescrever `erpcondominios`, bancos anteriores ou produção: o restore drill requer schema/VM temporário novo e isolado e transformação explicitamente testada; não improvisar `sed` sobre o dump. Até passar esse gate, o estado é “backup validado; restore drill e cópia off-host pendentes”.

## Logs

`logrotate` nativo é executado pelo timer do sistema. `erpcondominios-mysql.logrotate` mantém oito rotações semanais de error/slow logs; arquivos novos ficam `mysql:mysql 0600` porque consultas lentas podem carregar valores. A regra chama `mysqladmin flush-logs` por socket. `general_log=OFF`. Nginx e PHP-FPM usam as regras nativas; logs do sistema e dos timers ficam no journal. Não copiar linhas brutas para Git ou relatório.

## Rollback e critérios de parada

Rollback de código: apontar `current` para o symlink de release anterior preservada e validar Nginx. DDL H3 é additivo; rollback de banco requer restaurar o backup pré-DDL em uma cópia isolada ou desenvolver rollback explícito, nunca apagar colunas/tabelas automaticamente. Parar e pedir aprovação antes de DML migration, mudança em HostGator/DNS, integração externa real, exclusão de dados não temporários ou merge em `main`.

## Alertas de operação

O dispatcher `/usr/local/lib/erpcondominios/alert-manager.py` usa `/etc/erpcondominios/secrets/msmtprc` e credenciais separadas `titan-app-password` e `smtp-password`, todos `root:root 0600` no diretório `root:root 0700`. A conta `titan` (`smtp.titan.email`, 465/SSL-TLS) é primária; em rejeição/falha de transporte conclusiva, o código tenta `brevo`, que usa TLS conforme sua configuração. Em timeout ambíguo, o fallback é omitido para reduzir risco de envio duplicado; a notificação fica pendente para retry. Remetente e destinatário permanecem `noreply@erpcondominios.com.br`. O fallback é explícito por conta msmtp, não uma tentativa de dois provedores em paralelo. Cada conta usa `passwordeval` apontando para seu arquivo privado. TLS e verificação de certificado permanecem obrigatórios; logging de protocolo e syslog do msmtp ficam desligados. A origem da configuração Brevo continua sendo o dump-fonte confirmado pelo administrador, não a HML; não abrir nem copiar credenciais para Git, webroot ou chat.

O timer `erpcondominios-summary.timer` envia resumo todo dia às 08:00 `America/Sao_Paulo`, mesmo com falhas. O conteúdo inclui apenas status de serviços, ping MySQL, HTTPS, tamanho/horário do backup, integridade, validade do certificado, espaço livre, uptime e total de IPs banidos pelo Fail2ban. O healthcheck acompanha serviços, DB, HTTPs, TLS <72h, disco <15 GiB, backup >36h e marcador de integridade >36h. Falhas de backup, integridade, healthcheck e Certbot acionam `OnFailure` sem linhas de journal.

O mesmo item tem no máximo uma notificação de falha a cada 60 minutos; recuperação é enviada uma vez quando o item volta ao normal. Erro de envio mantém a pendência e usa backoff de 15 minutos. A unit de healthcheck termina com sucesso após reportar os itens; cada condição degradada gera seu próprio alerta e não cria um alerta genérico duplicado. Falha do resumo diário aciona a categoria `summary_delivery_failure`; o healthcheck tenta notificá-la novamente quando o relay voltar a aceitar mensagens. Para instalar app password TITAN pelo console interativo, executar `sudo -n /usr/bin/python3 /usr/local/lib/erpcondominios/set-titan-app-password.py`; o programa lê duas vezes em entrada oculta, não imprime o conteúdo e grava o segredo root-only. Em seguida, executar `sudo -n /usr/bin/python3 /usr/local/lib/erpcondominios/configure-msmtp-failover.py` para validar configuração. Só após isso, o teste real controlado é `systemctl start erpcondominios-alert-test.service`; simulação segregada de falha e normalização: `sudo -n /usr/bin/python3 /usr/local/lib/erpcondominios/alert-manager.py simulate-cycle` (não altera espaço nem serviço real). `accepted` significa apenas aceite do relay SMTP, não confirmação de entrega/leitura na caixa postal. Sem comandos `msmtp --debug`/logs de protocolo.
